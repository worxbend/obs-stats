# obs-stats — working notes

A btop-style terminal dashboard for OBS Studio. Single Rust binary, no daemon.

## Layout

```
src/
  obs/        obs-websocket 5.x: protocol, auth, session task (client),
              request building and total decoding (codec), typed payloads
  metrics/    Snapshot (the model), History (ring buffers), alerts, derived rates
  config/     YAML schema, XDG paths, loading, secret resolution
  tui/        app (state machine), keys (keymap), mouse (pointer routing),
              command (`:` registry), views/, widgets/, run (terminal)
  notify.rs   desktop notifications, on their own thread
  probe.rs    one-shot collection, shared by `once` and the screenshot generator
  report.rs   the JSON shape `once` prints — a public contract
  cli.rs      clap definitions and flag→config layering
examples/
  screenshot.rs   renders real frames to docs/images/*.svg
```

The layers only depend downward: `obs` → `metrics` → `tui`. Keep it that way.

## Invariants worth preserving

**The UI performs no I/O.** `tui::app::App::handle` is a pure state transition
returning an optional `Command` for the session task. Only `tui::run` touches
the terminal. This is what makes the whole interaction model testable without a
TTY, and it is why the render loop can never block on OBS.

**The keymap stays a pure function.** `keys::resolve` is
`(overlay, pending, key) → Resolution`, with no access to app state. Multi-key
sequences — `<leader>uu`, `gg`, `]b` — work by threading the pending prefix *in*
rather than by holding it in the keymap. Keep it that way: it is what lets the
whole sequence machine be tested without a terminal, and it is why the which-key
popup and the help overlay can both be generated from `LEADER_MAP` and
`BINDINGS` without drifting from what the keys actually do.

**One registry behind `:` and the palette.** `tui::command::COMMANDS` is the
only place a command is defined. The `:` line parses against it and the fuzzy
palette flattens it. A test asserts every completion Tab can produce is a line
Enter can run, so completion can never hand the user something that errors.

**Click regions are re-registered every frame.** `App::begin_frame` clears
`Regions`, and each widget records where it drew. A rect that survived into a
frame where its widget did not draw would route clicks to something invisible.
Recording geometry is not I/O, so this stays in `app` where it is testable.

**The session task owns the socket.** It reconnects with backoff, polls on a
timer, and pushes `Update`s. The UI never awaits a round trip. A hung OBS must
degrade to a visibly stale dashboard, never a frozen terminal.

**Passwords never become strings that can be printed.** They live in
`error::Redacted`, whose `Debug` and `Display` both render `<redacted>`. The
config file has no password field at all — only the *name* of an environment
variable.

**Decoders are total.** Everything in `obs::stats` falls back to a default
rather than failing the poll. OBS adds fields between point releases and drops
others when an output is inactive; a dashboard that blanks out because one
number moved is worse than one showing a zero.

**Counters are per-stream where it matters.** `GetStats` reports totals since
OBS launched. `Snapshot` captures a baseline when a stream starts so the UI can
report "this stream". Don't regress this — it is the main thing the OBS stats
dock gets wrong.

**Glyphs in aligned columns must be single-width.** Emoji are double-width and
silently shift every column after them on that row. `View::icon` and the audio
row's mute marker are both covered by tests that assert this.

## Testing

`cargo test` — 526 tests, no terminal and no live OBS required. The TUI is
exercised through ratatui's `TestBackend`; the client through synthetic
`Update`s. Rendering tests cover every view × every theme, plus cramped
terminals, so a layout that underflows is caught.

Before committing:

```sh
cargo fmt --all
cargo clippy --all-targets -- -D warnings
cargo test
cargo run --example screenshot -- --demo   # must produce no git diff
```

CI fails if the screenshots drift from the code.

## Screenshots

`docs/images/*.svg` are generated by `examples/screenshot.rs`, which draws real
frames and serialises the cell buffer to SVG. Generation is deterministic — a
fixed frame counter and a triangle-wave pseudo-noise function, no RNG and no
wall-clock in the output.

Regenerate with `--demo` (synthetic data). Without the flag it uses a live OBS
if one answers, which is useful for eyeballing but not for committing.

`--text` dumps the layouts as plain text, which is the fastest way to check a
layout change; add `--ascii` to inspect the fallback rendering.

**The screenshots cannot catch background bugs.** The SVG writer resolves
`Color::Reset` to the theme's own background, so a widget that wipes the themed
background still looks correct in `docs/images` while exposing the terminal's
wallpaper in a real session — which is exactly how ratatui's `Chart` shipped a
transparent plot area in v0.1.1. `no_widget_punches_a_hole_in_the_themed_background`
asserts on the cell buffer instead, which is the ground truth. It sweeps every
view × overlay × pending prefix, because `Clear` — which every overlay draws —
resets the cells it covers, and whatever follows it has to repaint the
background. That is how the `:` command line briefly shipped a transparent
status row.

Note that ratatui's `Chart`, `Sparkline` and `Scrollbar` have no ASCII mode —
their axes and tracks are box-drawing and their series braille, block elements
or arrows — so `views::ascii_plot`, `views::ascii_bars` and
`widgets::scrollbar` stand in for them. A rendering test walks every view ×
overlay in ASCII mode and fails on any Arrows / Box Drawing / Block Elements /
Geometric Shapes / emoji codepoint, so this cannot silently regress.

**Alerts are about rate, not totals.** `metrics::alerts::Watcher` works on
per-poll deltas over a rolling window, with a threshold and a per-cause
cooldown, and only while an output is running. The first observation is a
baseline only, and a counter going backwards counts as zero — an output restart
must never look like a catastrophic loss.

**Notifications never touch the render loop.** `notify::Notifier` owns a thread
and a channel; `send` is fire-and-forget. Showing a notification is a
synchronous D-Bus round trip, so doing it inline would reintroduce exactly the
stall the architecture exists to avoid.

## Things that are deliberate

- **Read-only.** Selecting a scene does not switch it. This is a monitor.
- **No daemon.** The reference project (`obsctl-rs`) is daemon-first because it
  writes; a read-only dashboard does not need one.
- **Cursor clamps, never wraps.** Jumping from the newest log line to the oldest
  on one keypress is disorienting.
- **Pause freezes metrics but not connection state.** A paused dashboard must
  never hide the fact that OBS went away.
- **The banner outranks by severity.** A render-lag warning must not displace a
  "viewers are seeing stutter" banner that is still on screen.
- **Chart y-axes window in.** A 5.4–6.5 Mbps series on a 0–7 Mbps axis is a flat
  line. See `History::axis_range`.
